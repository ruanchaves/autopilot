---
name: hiring-posts-outreach
description: A simple LinkedIn outreach pipeline aimed at roles paying the target band (config.yaml pay, by default USD 7k-8k+ a month). Runs LinkedIn post searches of the form "<role> hiring" ("AI Engineer hiring", "AI Engineer LATAM hiring", "Forward Deployed Engineer hiring"...) directly in LinkedIn search, never through external search engines, and records every post that announces a hiring for the target role, taking the author, role, posted pay and stated region from the post alone, with no profile visits. Ranks the authors by the highest pay their posts state and then by explicit eligibility for the user's region; authors whose posts state neither pay nor region are ordered by the poster's likely country, judged by a lightweight LLM subagent from the name, headline and company on file, nearest to the user's country first. Drops posts under the pay floor or closed to the region, and contacts them in that order: a plain message to 1st-degree connections, otherwise connection requests with a note (20 a day, shared with recruiter-outreach), then InMails while credits last. Messages never state pay and never ask for a call, and every draft is reviewed before sending, by a lint command and a sales-expert read (references/review.md), for the phrases, rhythm and template reuse that mark a generated note, so the recipient accepts the invite. Use when the user wants to search LinkedIn hiring posts for their role, find who is hiring at the target pay, run the hiring-posts pipeline, or connect with the authors of hiring posts. recruiter-outreach is the fuller recruiter pipeline; this one is the quick lane.

# Hiring-posts outreach

The quick lane of recruiter outreach: search LinkedIn posts for "<role> hiring", rank the authors by what their post says, contact them best-first. No profile probing, no rubric, no company lane. Discovery sends nothing; contacting uses the same daily caps and the same contact ledger as recruiter-outreach, so nobody is contacted twice across the two skills.

**Paths**
- **Skill:** `<repo>/hiring-posts-outreach` (`<hp>`), where `<repo>` is the autopilot repo.
- **Script:** `<hp>/scripts/hiringposts.py`. It imports recruiter-outreach's `recruiters.py` and job-source-sweep's helpers, so both sibling folders must be present. `<hp>/scripts/names.py` holds the country list and the distance table for the origin tie-break; the country itself is judged by a subagent following `<hp>/references/origin.md`.
- **Data:** `<home>/hiring-posts/` (`leads.json`, `searches.json`, `work/<date>/`), with `<home>` from `config.yaml`. Contacts, daily counters and the per-company cap are recruiter-outreach's files in `<home>/recruiters/`.
- **Candidate:** `candidate` in `config.yaml`, `<home>/fit-rubric.md`, `resume.base`.

**Running the script.** With the runner from `config.yaml`: for `python: wsl`, `wsl.exe -e python3 /mnt/<repo>/hiring-posts-outreach/scripts/hiringposts.py <cmd>` (from Git Bash, first `export MSYS_NO_PATHCONV=1`). Below, `hiringposts <cmd>` is short for that. Every command prints JSON.

**Settings** (`config.yaml`): `hiring_posts.roles` (role names to search; default `role.title`), `hiring_posts.suffixes` (the words after the role: "hiring", "LATAM hiring", ...), `hiring_posts.extra_queries`, `hiring_posts.floor_usd_month` (default 7000), `hiring_posts.max_post_age_days` (30), `hiring_posts.query_cooldown_days` (2), `hiring_posts.scrolls_per_query` (4), `hiring_posts.fx_usd` (rates for non-USD pay). Caps, gaps, `max_per_company` and `cta_styles` come from `recruiter_outreach`; the pay target from `pay`; the Chrome from `browser_os` and `browser_parallel`. No setup step: it runs on the existing config. If `recruiter-outreach` is not in `setup_done`, run that skill's setup first, because its caps and permission to send are what this skill uses.

**Which Chrome.** Before any Chrome work, load `mcp__claude-in-chrome__list_connected_browsers` and `mcp__claude-in-chrome__select_browser`, list the browsers, and call `select_browser` with the deviceId whose `osPlatform` is `browser_os` (Windows), even when only one browser is listed or it is already `inUse`: the selection is per session, and an unattended run (`claude -p`, a scheduled task) has nobody to answer a browser-choice prompt. Never select the macOS Chrome (user rule 2026-10-15); if none on that OS is connected, say Chrome is unavailable and stop. Pass the chosen deviceId to every Chrome subagent and have it re-run `list_connected_browsers` once to confirm the `inUse` browser is on that OS. Then open one LinkedIn tab in the extension tab group (`tabs_context_mcp` with `createIfEmpty`) and keep it open for the whole run: the user wants to see the skill working in their Chrome, and subagents that open and close their own tabs look like a headless run. Say in chat which browser was selected.

## The run

Repeat **search → ingest → plan → contact → record** until `hiringposts status` says `done: true`, LinkedIn blocks, or the user says stop. `done` means today's connection requests are used, the InMail credits (or cap) are used, every 1st-degree lead in the pile has had its plain message, or the pile and the due phrasings are both empty. Finishing with budget unspent while phrasings are still due is not done.

### 1. Search

1. Run `hiringposts search-plan [--max-queries 12]`. It returns the phrasings due (never run, or run longer ago than `query_cooldown_days`; least recently run first), `known_posts`, `known_authors`, the region terms, the floor, the scroll count, and the `result` path. The phrasings are `roles × suffixes` plus `extra_queries`. When `due` is 0, say so and go to step 3 with the pile as it is; if the pile is empty too, add role synonyms or suffixes to `config.yaml` (for an AI engineer: "LLM Engineer", "Machine Learning Engineer", "GenAI Engineer", "Applied AI Engineer", "AI Solutions Engineer", "Forward Deployed Engineer", "Agents Engineer"; suffixes "hiring remote LATAM", "hiring Brazil", "contratando") and plan again.
2. **Search sequentially, in one tab.** Launch **one** Chrome subagent (`general-purpose`, `model: "sonnet"`) for the whole list, or run the phrasings yourself in the open LinkedIn tab: "Read `<hp>/references/search.md` and follow it. Run the phrasings one after another in a single tab, a few seconds between pages." followed by the `queries` and the rest of the plan. Never split the phrasings across parallel Chrome subagents: three parallel post searches got LinkedIn's "unusual search traffic" pause within two phrasings each on 2026-10-25, and the same happened to bulk LinkedIn paging on 2026-10-12. `browser_parallel` does not apply to LinkedIn search. The subagent works through the DOM tools and takes no screenshots. Search cards no longer expose post URLs; that is fine, the script keys such posts by author and text.
3. As each finishes, run `hiringposts ingest --result <file>`. It parses the posted pay into USD a month (annual ÷ 12, hourly × 160, other currencies through `fx_usd`), reads eligibility from the region words, drops posts under the floor, closed to the region, at banned companies or older than the window, marks each new no-pay no-region author as `origin pending`, and reports `pile`, `with_pay`, `first_degree`, `origin` (the no-pay, no-region leads: how many are `pending`, the judged ones by country, how many the judge could not place) and the top of the ranking. If it reports `blocked: true`, stop searching for today.
4. **Judge the origins** before planning. Run `hiringposts origin-plan`: it lists every lead whose order depends on the poster's country (tier 1, eligibility `unclear`) and that has not been judged yet, each with `profile_url`, `name`, `headline` and `company`, plus `home_country`, the `countries` the script accepts, `judge_reference` and the `result` path. Skip this step when `leads` is empty. Otherwise launch **one lightweight subagent** (`general-purpose`, `model: "haiku"`, no browser, no search) with the prompt: "Read `<judge_reference>` and follow it. Write the result to `<result>`." followed by `home_country`, `countries` and the `leads` list as JSON. It answers from the three strings only; up to about 80 leads go in one subagent, more are split into parallel subagents with their own `result` files (add a suffix). When it finishes, run `hiringposts origin --result <file>` for each file: it stores the countries, folds common spellings (USA, United Kingdom, South Korea...), keeps a `null` as a real "cannot tell" at the unknown distance, reports any country it could not place under `unknown_country_skipped` (those leads stay pending: fix the spelling and run `origin` again, or leave them at the unknown distance), and re-ranks. Do not judge names yourself in chat, and do not visit profiles: the subagent, reading what is already on file, is the only judge. A lead is judged once; `origin-plan --all` relists judged leads when you want a second opinion, and a later `origin` overwrites.

### 2. Rank

The pile is sorted on ingest and shown by `hiringposts rank`:

1. **Tier 0** first: authors whose posts state pay at or above `floor_usd_month`, highest pay first.
2. **Tier 1** after: authors whose posts state no pay.
3. Inside each tier, explicit eligibility for the candidate's region first (`latam`: the post names the country, the region or one of its aliases or countries), then `worldwide` (anywhere / global), then `unclear` (remote, region unstated). Newest post breaks ties.
4. **Tier 1 `unclear`** (no pay stated, no region words): with nothing in the post to go on, the poster's likely country is judged by a lightweight LLM subagent (`references/origin.md`) from the name, headline and company on file, and these leads are ordered by how far that country is from the candidate's country, nearest first (a Brazilian poster at 0 km, then Argentina, Hispanic LATAM, the US, Europe, the Middle East, Asia). The judge reads the headline and company first (a city, a language, a company based somewhere), then the surname for heritage and the first name for the diaspora (an Italian surname with a Portuguese first name is Brazil, with a Spanish first name Argentina; an Anglo first name on an East Asian or Indian surname is the US); Portuguese names are Brazil and Spanish names with no country marker sit at a generic Hispanic LATAM point (Colombia's distance). `names.py` only holds the accepted country list and the distances. Leads not yet judged, and leads the judge could not place, sort at the unknown distance (9,000 km: after the Americas and Iberia, before Asia), so an unreadable name is neither rewarded nor buried. Newest post breaks ties at the same distance. The judgement only orders this group: it never drops a lead, never changes a tier, and never appears in a message.
5. **Out** (never contacted): posts whose highest pay is under the floor, posts limited to another region or to US work authorisation, on-site or hybrid elsewhere, banned companies, posts older than `max_post_age_days`, and authors already contacted by any skill (the shared `contacts.json`).

### 3. Contact

1. Run `hiringposts plan --n 40`. It writes a task file with the ranked pile cut to today's budget (every contactable 1st-degree lead plus as many others as connection requests and InMails remain), each task carrying the post, the rank (with the judged `origin` for tier-1 `unclear` leads, for the record only), the degree and a `cta`, plus `quotas`, `candidate`, the paths and the `result` file. Leads at a company already at `max_per_company` are listed under `deferred_company_cap` and left out.
2. Launch **one** Chrome subagent (`general-purpose`, `model: "sonnet"`): "Read `<hp>/references/message.md` and follow it; it points you to the recruiter-outreach message rules and to the pre-send review in `<hp>/references/review.md`. No draft goes into LinkedIn before `hiringposts lint` says `send` and the review reads clean." followed by the task file's contents and the exact `hiringposts` command prefix for `check` and `lint`. Sending is always a single subagent (user rule 2026-10-10).
   - **The review** (`references/review.md`) is the sales-and-communication pass: the goal of every note is that the recipient accepts the invitation, so each draft is read as the recipient reads it (first line and headline, two seconds, on a phone) and rewritten when it shows a generated-text marker (stock openers, corporate vocabulary, borrowed enthusiasm, lists of three, dashes, a summarising close, a question at the end), résumé prose, hedging, the wrong register for the post, a claim the resume does not back, or the skeleton of the last notes sent. `hiringposts lint` does the deterministic part (the phrases, the dash, the question, the call ask, the pay mention, the missing why-them clause, and 4-gram overlap with everything sent in the last 60 days across both outreach skills); the subagent does the judgement.
3. Run `hiringposts record --result <file>`. It writes the contacts into the shared ledger and counters through recruiter-outreach's `record`, marks this skill's leads contacted, skipped or deferred, and lints every sent message again: `lint_flags` lists the ones that went out with a failing check, which the report must show.
4. Run `hiringposts status`. If `done` is false and nothing blocked: when `contactable_now` is 0 and `queries_due` > 0, go back to search; otherwise plan again.

## Report

At the end, in chat: phrasings run and posts kept per phrasing (`searches.json`), the pile by tier and eligibility, the no-pay no-region leads by judged country (`rank` → `origin`), how many the judge could not place and how many were still pending, the top ten with pay and region words (and the judged origin where it decided the place), messages sent by channel with the full text of each (the user audits the writing), any `lint_flags` from `record` and the highest `reuse` share of the day, connection requests and InMail credits left (both should be zero; if not, why), the leads left for tomorrow and anything LinkedIn blocked. Recruiter-outreach's `recruiters dashboard` and the role explorer's Outreach view show these contacts too, since they share `contacts.json`.

## Rules

- Post evidence only: no profile visits during search, and the message is built from the post. The origin judgement comes from a lightweight subagent reading the name, headline and company already recorded, never from a profile visit or a search, and it is never said or implied to the person.
- Never state pay, never ask for a call; English always; the close is an open door or a CV offer (`recruiter-outreach/references/message.md`).
- Every draft passes `hiringposts lint` and the review in `references/review.md` before it is inserted: no generated-text markers, no template reuse, read as the recipient reads it. The purpose of the note is an accepted invite, so a note that is correct but sounds machine-made is rewritten, never sent.
- Nobody is contacted twice across skills; current employers (`banned_companies`) never.
- 20 new connection requests a day across recruiter-outreach and this skill together; 1st-degree messages never count toward it.
- Searching happens only inside LinkedIn's own post search, never through Google or other engines.
- One LinkedIn search tab at a time, phrasings run one after another with a few seconds between pages; never parallel search subagents (LinkedIn pauses search, 2026-10-12 and 2026-10-25). Sending is one subagent too (user rule 2026-10-10).
- Always select the Windows Chrome explicitly with `select_browser` at the start of the run and leave one LinkedIn tab open in your Chrome for the whole run (user rule 2026-10-25); the run is never headless.
